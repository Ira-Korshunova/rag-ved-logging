# Разъяснение кода по модулям

Пошаговое объяснение каждого файла проекта «RAG-ассистент по ВЭД». Простым языком, с аналогиями, в порядке выполнения — от запуска до ответа.

---

## Карта проекта

```
app.py            ← точка входа: консоль, в которую ты пишешь вопросы
rag_pipeline.py   ← дирижёр: кеш → поиск → промпт → LLM → кеш
vector_store.py   ← библиотека: хранит документы в виде векторов и ищет похожие
cache.py          ← память: сохраняет готовые ответы, чтобы не звать LLM повторно
evaluate_ragas.py ← экзаменатор: оценивает качество ответов (опционально)
data/             ← сами ВЭД-документы (база знаний)
.env              ← настройки: ключи, модели, параметры
```

Аналогия: представь библиотеку.
- `data/` — полки с книгами (ВЭД-документы).
- `vector_store.py` — каталог, где каждая книга разложена на «векторы-карточки», и ты находишь нужные по смыслу, а не по совпадению слов.
- `rag_pipeline.py` — библиотекарь, который берёт карточки, читает вопрос и формирует ответ.
- `cache.py` — тетрадь с готовыми ответами на уже заданные вопросы.
- `app.py` — окошко, за которым сидишь ты и задаёшь вопросы.
- LLM (qwen3.7-max) — сам «мозг», который пишет ответ по контексту.

---

## 1. `app.py` — точка входа (консоль)

**Что делает:** запускает приложение, показывает баннер, в цикле читает твои вопросы, передаёт их в `RAGPipeline` и печатает ответ.

Ключевые места:

1. **Загрузка `.env`**
   ```python
   env_path = Path(__file__).parent.parent / '.env'
   load_dotenv(env_path)
   ```
   Берёт настройки (ключ, модель, эндпоинт) из файла `.env` в корне проекта и кладёт их в переменные окружения, чтобы остальные модули могли их читать через `os.getenv(...)`.

2. **`print_banner()`** — рисует баннер с моделью и эндпоинтом (читаются из `.env`).

3. **Проверка ключа**
   ```python
   if not os.getenv("OPENAI_API_KEY"):
       ... sys.exit(1)
   ```
   Если ключа нет — сразу останавливаемся, бесполезно идти дальше.

4. **Создание pipeline**
   ```python
   pipeline = RAGPipeline(
       collection_name="api_rag_collection",
       cache_db_path="api_rag_cache.db",
       data_file="data"
   )
   ```
   `data_file="data"` — это **папка**, а не файл. Поэтому индексируются все ВЭД-документы. Модель берётся из `MODEL_NAME` (qwen3.7-max).

5. **Главный цикл** — `while True:` читает `input("💭 Ваш вопрос: ")`:
   - `exit/quit` → выход;
   - `stats` → статистика (чанков, размер кеша, модель);
   - `clear` → очистить кеш;
   - иначе → `pipeline.query(...)` и `print_response(...)`.

6. **`print_response(result)`** — красиво печатает вопрос, источник (кеш или LLM), сам ответ и 3 использованных фрагмента контекста с указанием файла-источника `[имя_файла]`.

## 2. `rag_pipeline.py` — дирижёр конвейера

**Что делает:** оркестрирует весь поток «вопрос → ответ» по 5 шагам.

### `__init__` — настройка
- `self.model = model or os.getenv("MODEL_NAME", "gpt-4o-mini")` — модель из `.env`.
- `self.top_k = int(os.getenv("TOP_K", "3"))` — сколько документов отдавать в контекст.
- Создаёт OpenAI-совместимый клиент, подставляя `base_url` из `.env` (DashScope):
  ```python
  client_kwargs = {"api_key": os.getenv("OPENAI_API_KEY")}
  if base_url:
      client_kwargs["base_url"] = base_url
  self.openai_client = OpenAI(**client_kwargs)
  ```
- Создаёт `VectorStore` (библиотеку).
- Если коллекция пустая — грузит документы: если `data_file` это папка → `load_documents_from_folder`, если файл → `load_documents`.
- Создаёт `RAGCache` (тетрадь с ответами).

### `query(user_query, use_cache=True)` — главный метод
Пять шагов:

1. **Проверка кеша.** `self.cache.get(query)` — если вопрос уже был, сразу возвращаем готовый ответ (быстро, бесплатно, LLM не дёргаем).
2. **Поиск релевантных документов.** `self.vector_store.search(query, top_k=self.top_k)` — возвращает N самых похожих по смыслу фрагментов.
3. **Формирование промпта.** `_create_prompt(query, context_docs)` — собирает текст «вот контекст, вот вопрос, ответь по нему и укажи источники».
4. **Генерация ответа.** `_generate_answer(prompt)` — звонок в LLM (qwen3.7-max) через `chat.completions.create`.
5. **Сохранение в кеш.** `self.cache.set(query, answer, context)` — чтобы в следующий раз не звать LLM.

### `_create_prompt` — сборка промпта
Каждый документ помечается источником:
```python
context_parts.append(f"Документ {i} [источник: {source}]:\n{doc['text']}\n")
```
В инструкции модели добавлено: «в конце ответа укажи, из каких документов взята информация, в квадратных скобках». Поэтому в ответе появляется `[источник: …]`.

### `_generate_answer` — звонок в LLM
```python
response = self.openai_client.chat.completions.create(
    model=self.model,
    messages=[{"role": "system", ...}, {"role": "user", "content": prompt}],
    temperature=0.3,
    max_tokens=500
)
```
`temperature=0.3` — низкая, чтобы ответ был точным, а не «творческим» (для фактических ВЭД-вопросов это правильный выбор).

## 3. `vector_store.py` — векторная библиотека (ChromaDB)

**Что делает:** хранит документы в виде векторов (эмбеддингов) и находит самые похожие по смыслу. Это сердце RAG.

### `__init__`
- Создаёт персистентный клиент ChromaDB (`PersistentClient`) — данные живут на диске в `chroma_db/`.
- Берёт или создаёт коллекцию с косинусным расстоянием (`"hnsw:space": "cosine"`).
- Создаёт OpenAI-совместимый клиент для эмбеддингов (с `base_url` из `.env`).
- `self.embedding_model = os.getenv("EMBEDDING_MODEL", "text-embedding-v3")`.

### `_chunk_text(text, chunk_size=500, overlap=100)` — нарезка на чанки
Зачем: длинный документ нельзя скормить в поиск целиком — нужен кусок «по размеру контекста». Стратегия:
- режем по абзацам (`\n\n`);
- если абзац длиннее `chunk_size` — режем по предложениям;
- `overlap=100` — соседние чанки перекрываются на 100 символов, чтобы не разорвать мысль на границе;
- выбрасываем чанки короче 50 символов (мусор).

### `_create_embedding(text)` — превращение текста в вектор
```python
response = self.openai_client.embeddings.create(input=text, model=self.embedding_model)
return response.data[0].embedding
```
Текст → числовой вектор (массив чисел). Похожесть векторов = похожесть смысла. Идёт через DashScope (`text-embedding-v3`).

### `load_documents_from_folder(folder_path)` — индексация всех документов
(Метод, который я добавил вместо одного файла.)
- Проверяет, что коллекция пустая (чтобы не задваивать).
- Берёт все `.txt`/`.md` из папки.
- Каждый файл: читает → `_chunk_text` → для каждого чанка делает embedding → складывает в списки `documents/ids/embeddings/metadatas`.
- В `metadatas` кладёт `{"source": file_name}` — чтобы потом знать, из какого файла кусок.
- `ids.append(f"{file_name}_{chunk_counter}")` — id содержит имя файла (фолбэк, если метаданных нет).
- Одним батчем `self.collection.add(...)` добавляет всё в ChromaDB.

### `search(query, top_k)` — поиск релевантных
- Делает embedding запроса.
- `self.collection.query(query_embeddings=[...], n_results=top_k)` — ChromaDB ищет ближайшие векторы.
- Форматирует результат: для каждого найденного куска берёт `source` из метаданных (или из id как фолбэк) и возвращает список словарей `{id, text, source, distance}`.

### `get_collection_stats()` — статистика для команды `stats`
Возвращает имя коллекции, число чанков, директорию.

## 4. `cache.py` — кеш ответов (SQLite)

**Что делает:** сохраняет пары «вопрос → ответ», чтобы повторные вопросы не шли в LLM (экономия и скорость).

### Идея
Ключом служит не сам вопрос (длинный), а его **хеш** — короткий фиксированный идентификатор:
```python
normalized_query = " ".join(query.lower().strip().split())
query_hash = hashlib.sha256(normalized_query.encode()).hexdigest()
```
Нормализация: lowercase + схлопывание пробелов → «Что такое УНК? » и «что такое унк?» дадут одинаковый хеш (один ответ на оба варианта).

### Таблица SQLite
```sql
CREATE TABLE IF NOT EXISTS cache (
    query_hash TEXT PRIMARY KEY,   -- хеш вопроса (ключ)
    query TEXT NOT NULL,            -- сам вопрос
    answer TEXT NOT NULL,           -- ответ LLM
    context TEXT,                   -- JSON со списком использованных документов
    created_at TIMESTAMP             -- когда закешировано
);
```

### Методы
- `set(query, answer, context)` — `INSERT OR REPLACE`: сохраняет или обновляет запись. Контекст сериализуется в JSON.
- `get(query)` — ищет по хешу; если найдено — возвращает `{query, answer, context, created_at, from_cache=True}`, иначе `None`.
- `clear()` — `DELETE FROM cache` (команда `clear` в консоли).
- `get_stats()` — сколько записей, размер БД, даты первой/последней записи.

Зачем нужен: одинаковые вопросы (а студенты часто переспрашивают одно и то же) отдаются мгновенно и бесплатно. Минус — если база знаний изменилась, старый ответ может устареть; тогда `clear`.

## 5. `evaluate_ragas.py` — оценка качества (опционально)

**Что делает:** прогоняет 5 ВЭД-вопросов через RAG и считает метрики RAGAS.

### Метрики
- **Faithfulness** (точность ответа) — насколько ответ опирается на контекст, а не выдуман (0.0–1.0).
- **Context Precision** (точность контекста) — насколько найденные документы реально релевантны вопросу.

### Как работает
1. Готовит 5 ВЭД-вопросов (`EVALUATION_QUESTIONS`).
2. `prepare_dataset()` — прогоняет каждый вопрос через `pipeline.query(..., use_cache=False)`, собирает `{question, answer, contexts, ground_truth}` в `Dataset`.
3. Настраивает «судью» и эмбеддинги для RAGAS **через тот же DashScope** (иначе RAGAS по умолчанию звал бы `gpt-4o`, которого в DashScope нет):
   ```python
   judge_llm = ChatOpenAI(model=MODEL_NAME, base_url=OPENAI_BASE_URL, api_key=...)
   judge_embeddings = OpenAIEmbeddings(model=EMBEDDING_MODEL, base_url=..., api_key=...)
   result = evaluate(dataset=dataset, metrics=metrics, llm=judge_llm, embeddings=judge_embeddings)
   ```
4. Считает средние значения, печатает оценку (отлично/удовлетворительно/требует улучшения) и детали по каждому вопросу.

Запуск: `python evaluate_ragas.py` (не обязателен для сдачи, но подтверждает качество).

## 7. `.env` — настройки

| Переменная | Значение | Кто читает |
|---|---|---|
| `OPENAI_API_KEY` | ключ DashScope | все модули |
| `OPENAI_BASE_URL` | эндпоинт DashScope | pipeline, vector_store, evaluate_ragas |
| `MODEL_NAME` | qwen3.7-max | pipeline, app (баннер), evaluate_ragas |
| `EMBEDDING_MODEL` | text-embedding-v3 | vector_store, evaluate_ragas |
| `TOP_K` | 7 | pipeline (число документов в контекст) |

Важная особенность: это **OpenAI-совместимый** API. Код написан под OpenAI-SDK, а `base_url` подменяет эндпоинт на DashScope — поэтому работают модели Qwen. Один ключ — для генерации и эмбеддингов.

## Порядок выполнения одного запроса (полный путь)

Например, ты вводишь: «Что такое аккредитив?»

1. `app.py`: `input()` → `pipeline.query("Что такое аккредитив?")`.
2. `rag_pipeline.query`:
   - **Кеш:** `cache.get("Что такое аккредитив?")` → `None` (первый раз) → идём дальше.
   - **Поиск:** `vector_store.search("Что такое аккредитив?", top_k=7)`:
     - `vector_store._create_embedding("Что такое аккредитив?")` → вектор запроса (звонок в DashScope `text-embedding-v3`);
     - ChromaDB находит 7 ближайших по косинусу чанков → возвращает `[{text, source, distance}, ...]`.
   - **Промпт:** `_create_prompt` собирает «Документ 1 [источник: ved_payments.txt]: …» + вопрос + инструкции.
   - **Генерация:** `_generate_answer(prompt)` → звонок в `qwen3.7-max` (через `chat.completions.create`) → текст ответа.
   - **Кеш:** `cache.set("Что такое аккредитив?", answer, context)` → записано в SQLite.
3. `app.py`: `print_response(result)` печатает ответ, источник (LLM), 3 фрагмента контекста с именами файлов.
4. Второй раз тот же вопрос → шаг «Поиск/Промпт/Генерация» пропускается, ответ берётся из кеша → `Источник: КЕШ`.

## Где что подкрутить

- Хочешь больше документов в ответе → `TOP_K=10` в `.env`.
- Хочешь другой Qwen → `MODEL_NAME=qwen3.6-plus` (или `qwen3.6-flash`, он быстрее/дешевле).
- Хочешь «креативнее» ответы → `temperature` в `_generate_answer` поднять до 0.7.
- Хочешь пересобрать базу → `rm -rf chroma_db` и `python app.py`.
- Хочешь добавить документ → кинь `.txt` в `data/`, удали `chroma_db`, запусти.
