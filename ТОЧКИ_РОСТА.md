# Точки роста rag-ved-logging — что ещё определяет качество ответа

*Записано 30.09.2026 из экспертного разбора (текст Ирины, собран с внешним анализом).
Стартовое состояние: BGE-M3 local + Chroma + cache + DeepSeek + логи (ДЗ 8.9).*

---

## 0. Постановка

Эмбеддер отвечает только за поиск и представление текста. Качество итогового
ответа в нормативном RAG определяют: **чанкинг, гибридный поиск, reranking,
актуальность редакций НПА, LLM-генератор** — то есть архитектура в целом.

BGE-M3 — открытая мультиязычная embedding-модель BAAI (MIT): 100+ языков,
контекст до 8192 токенов, 1024-мерные вектора, три типа поиска (dense — смысл,
sparse — слова/термины, ColBERT-подобный multi-vector). Для ВЭД, где запросы
смешанные («ставка пошлины на код ТН ВЭД 8471…» + русская формулировка, но
английские invoice / packing list / bill of lading — точные совпадения кодов,
номеров решений ЕЭК и дат), это делает её функционально сильнее типичного
облачного эмбеддинга как основу гибридного retrieval. На задаче нахождения
релевантных нормативных фрагментов сопоставима с облачными и иногда лучше;
«облако лучше во всём» — неверная постановка. Нюанс честности: бенчмарки BAAI
нельзя напрямую переносить на российские/евразийские нормы — качество на своём
корпусе надо измерять (см. § 6, золотой набор).

Ограничение честности: у нас уже зафиксировано в ответе формы — при базе ~165
чанков разница эмбеддеров внутри погрешности; реранкер осознанно отложен
(малая база, лишний платный вызов).

## 1. Версионность и дата действия нормы (юридическая надёжность)

Хранить для каждого фрагмента: наименование НПА, орган и юрисдикцию (ЕАЭС, ЕЭК,
ФТС, РФ, ЕС…), номер/статью/пункт/подпункт, дату принятия, дату вступления в
силу, дату утраты силы, редакцию и период действия, источник публикации,
ссылку на первоисточник. Без этого ассистент уверенно выдаст отменённую ставку
или старый порядок декларирования. Минимальный набор метаданных:

```json
{
  "document_id": "eaeu_customs_code",
  "title": "Таможенный кодекс Евразийского экономического союза",
  "jurisdiction": "EAEU",
  "authority": "Евразийский экономический союз",
  "document_type": "code",
  "article": "104",
  "paragraph": "2",
  "edition_date": "2026-01-01",
  "valid_from": "2026-01-01",
  "valid_to": null,
  "status": "active",
  "topic_tags": ["customs_declaration", "declaration"],
  "source_url": "...",
  "source_hash": "...",
  "language": "ru"
}
```

Политика ответа LLM: только по переданным источникам; показать цитаты;
при недостаточности данных — «в базе не найдено достаточных оснований,
требуется проверка источника». Дополнительно для запросов вида «ввоз
оборудования из Китая» — сначала уточнить: применимое право, статус
импортёра/декларанта, код ТН ВЭД / CN, назначение (продажа / временный ввоз /
ремонт / выставка), страну происхождения, Incoterms, дату операции,
лицензии/сертические/санкционные ограничения.

## 2. Гибридный поиск вместо vector-only

Для ВЭД нужен не только semантический поиск (dense): BM25/sparse ловит точные
сущности («Решение ЕЭК № 130», «статья 104 ТК ЕАЭС», «код 8471…», «ДТ», «КТС»),
metadata filtering ограничивает юрисдикцию/период/редакцию, reranker
финально пересортитывает кандидатов. Формула:

    Score = α·Dense + β·Sparse(BM25) + γ·Metadata + δ·Reranker

Рекомендуемая цепочка: BGE-M3 (dense + sparse) и BM25 достают 30–50 кандидатов
→ reranker оценивает пары «вопрос → фрагмент» → в LLM уходят 4–8 лучших →
ответ + статья/пункт + редакция + дата действия + ссылка на источник.
Reranking — один из ощутимых способов поднять точность (обзоры production RAG),
добавляет десятки–сотни мс.

## 3. Чанкинг по юридической структуре

Сейчас чанк = 500 символов + overlap 100 (по абзацам). Точка роста: нарезка по
юридической иерархии — документ → раздел → глава → статья → пункт/подпункт,
с метаданными (статья/пункт/редакция), чтобы контекст приходил целыми
логическими единицами и его можно было фильтровать.

## 4. Инструменты

- retrieval: `BAAI/bge-m3` (dense + sparse);
- reranker: `BAAI/bge-reranker-v2-m3` (локальный, ~30–50 мс);
- индекс: Qdrant / OpenSearch / Elasticsearch — векторный + BM25 + фильтры
  метаданных (сейчас Chroma-файл, его хватает до десятков тысяч чанков);
- LLM: отдельно от retrieval-сервиса; облачный генератор допустим как
  premium-режим для сложных сравнений/анализа контракта.

Ресурсы BGE-M3: ~568 млн параметров, веса ~2.3 ГБ. На CPU — ок для query-
эмбеддингов (10–50 мс ≈ 1% времени ответа) и пакетной индексации; при больших
объёмах или связке с GPU-LLM — планировать батчи/отдельный сервис. Лёгкие
E5 (`multilingual-e5-small/base`) — вариант для совсем слабых машин или A/B.

## 5. Деньги

- облачные embeddings растут с объёмом индексации и запросов, дают MLOps «из
  коробки»; self-hosted — почти фиксированная стоимость, полный контроль
  данных (закрытый контур), предсказуемые версии и лимиты;
- отраслевая оценка точки перехода cloud→self-hosted ≈ 2000–2500 запросов/день
  (зависит от цен, reranking, кеша и т. п.);
- embeddings обычно не главная статья бюджета облака: деньги съедают длинные
  контексты в LLM, отсутствие кеша (у нас кеш уже есть), переиндексация без
  инкремента, крупные чанки, top-20 вместо top-5.

## 6. Измеримость (уже в проекте, усилить)

В проекте уже есть измерительный контур — логирование 5 событий + /stats +
RAGAS (`evaluate_ragas.py`). Точки роста оценивать в цифрах: собрать «золотой
набор» 100–300 реальных вопросов по ВЭД (правильный документ/статья/допустимый
ответ) и сравнить контуры:

- BGE-M3 dense only → dense + BM25 → hybrid + reranker;
- метрики: Recall@5, nDCG@10, доля ответов с верной цитатой, доля ответов по
  отменённой редакции, latency p50/p95, стоимость одного ответа.

Так каждая точка роста из списка доказывается числами «до/после» — это и есть
сериальность портфолио-кейса.

## 7. Рекомендованная целевая архитектура (для роста)

```
Источники НПА / разъяснения / классификаторы / шаблоны
  ↓ ETL: OCR → очистка → дедупликация → метаданные редакций
  ↓ чанкинг по юридической структуре (статья → пункт)
  ↓ BGE-M3: dense + sparse
  ↓ Qdrant/OpenSearch: vector + BM25 + фильтры метаданных
  ↓ top-30 → reranker → top-5
  ↓ LLM с жёстким правилом «только по переданным источникам, цитаты,
    при недостаточности — отказ»
  → Ответ + статья/пункт + редакция + дата действия + источник
```

## 8. Наши приоритеты (адаптировано к текущему состоянию)

1. **Гибрид (BM25-слой)** — самый дешёвый выигрыш, локальный, добавит точные
   совпадения по номерам статей и кодам ТН ВЭД.
2. **Локальный реранкер** `bge-reranker-v2-m3` — при росте базы (сейчас осознанно
   отключён).
3. **Чанкинг по структуре НПА + метаданные редакций** — юридическая надёжность,
   самый сложный пункт; начать с полей `edition/valid_from/status` в метаданных
   чанков при следующем инжесте.
4. **Золотой набор вопрос → правильный источник** — 30–50 вопросов достаточно
   для первого A/B (в масштабе урока: это расширение существующего RAGAS-скрипта).
5. Хранить версию эмбеддинг-модели рядом с индексом (векторы несовместимы — уже
   есть практика бэкапов `chroma_db_v3_backup/`). Локальная модель ещё и снимает
   зависимость от смены политик/лимитов облачных API (наш случай: квоты
   DashScope выжигаются фритирами).
